# Adsterra Low-Interruption Integration Design

Date: 2026-08-24
Status: Approved in the Codex task

## Purpose

Add the two approved Adsterra units to the existing static Astro site without changing the framework, domain, URL structure, content files, or Cloudflare project. Advertising appears only on generated guide article pages. Local development, automated tests, and ordinary previews render inert placeholders and make no Adsterra requests. The verified production deployment loads the real units when all relevant switches are enabled.

Approved inventory:

- Domain: `howtofishgamehelp.com`
- Adsterra Website ID: `6003596`
- Native Banner Ad Unit ID: `30895300`
- Banner 320x50 Ad Unit ID: `30895328`

No Social Bar, Popunder, Interstitial, Smartlink, Direct Link, or unapproved format is in scope.

## Existing architecture

The project uses Astro 7.2.4 with TypeScript, static output, trailing-slash routes, Astro content collections, Markdown guide entries, Pagefind, and a Cloudflare Worker serving static assets. All published guide articles are generated by `src/pages/[category]/[slug].astro`, rendered through `src/layouts/GuideLayout.astro`, and sourced from the `guides` collection in `src/content.config.ts`.

The current 31 published guides all contain a `Quick steps` H2 followed by another H2, and all end their Markdown body with `What to do next`. `Sources and verification` is a separate layout-owned section after the Markdown body. There is no Astro ClientRouter, View Transitions integration, SPA router, or partial-page navigation. Normal guide-to-guide navigation performs a complete page load.

The existing Worker applies a Content Security Policy. The repository does not configure Cloudflare Rocket Loader; its live zone setting must be checked separately during release verification. The Native Banner's `data-cfasync="false"` attribute remains unchanged regardless of that setting.

## Selected approach

Use the existing eagerly rendered content result and perform a build-time, node-safe split of the rendered guide HTML. Add `parse5` as a development dependency so the split operates on complete HTML nodes. Do not use regular-expression replacement, uncontrolled string slicing, a client-side DOM query, or post-load movement.

This is preferred over changing Astro's Markdown processor because Astro 7 uses its current Markdown processor by default, while a custom remark or rehype pipeline would add a processor dependency and broaden the content-rendering change. It is also preferred over placing the banner at a fixed layout position because every current guide has a precise `Quick steps` boundary.

`parse5` is build-only. It is not bundled into page JavaScript, the Cloudflare Worker, or either Adsterra script.

## Structured Quick steps split

Create a focused helper under `src/lib/ads/` that accepts a guide route and Astro's rendered HTML and returns one of two results:

- a successful split containing `beforeBanner` and `afterBanner`; or
- a skipped result containing the route and a human-readable reason.

The helper parses the full rendered body as an HTML fragment and inspects top-level sibling nodes in document order:

1. Find a top-level `h2` element whose `id` attribute is exactly `quick-steps`.
2. Starting after that node, find the next top-level `h2` sibling.
3. Treat the `h2#quick-steps` node and every complete sibling node before the next H2 as the full Quick steps section.
4. Serialize complete nodes through the end of that section as `beforeBanner`.
5. Serialize the next H2 and all remaining complete nodes as `afterBanner`.

The 320x50 component is rendered between those two fragments. The split therefore cannot land between the Quick steps heading and its list, or inside a list, paragraph, link, code block, or unclosed tag.

If the Quick steps heading or its same-level boundary cannot be recognized, the page renders the original complete Astro `Content` component and omits only the 320x50 unit. It does not fall back to Direct answer and does not move the advertisement elsewhere.

`getStaticPaths()` processes the guide collection as one set, so it can:

- emit one warning per skipped guide, including the full guide route;
- emit one final summary listing every skipped route, or explicitly report zero skipped routes;
- continue the build for isolated content exceptions; and
- fail the build when at least 80% of guide pages cannot be split, because that indicates the placement logic or renderer contract has broadly failed.

## Components and final positions

Create these independent Astro components under `src/components/ads/`:

- `AdsterraBanner320x50.astro`
- `AdsterraNativeBanner.astro`

Both components render a normal-flow `aside` with `aria-label="Advertisement"` and a visible `Advertisement` label. Neither component uses fixed, sticky, overlay, or content-disguising styles.

### 320x50 Banner

The production branch preserves this exact execution contract:

- the classic `atOptions` configuration script executes first;
- key `31358e95bdfca07885ad4d825c43845b` remains unchanged;
- format remains `iframe`;
- height remains `50` and width remains `320`;
- params remains an empty object;
- `https://www.highrevenueformat.com/31358e95bdfca07885ad4d825c43845b/invoke.js` executes second;
- neither script is a module and neither receives `async` or `defer`.

Astro `is:inline` is used only as a compiler directive so the classic script order and source text survive the build. The unit appears once, after the entire Quick steps block and before the next main H2.

The ad body has an exact 320x50 reserved area. Its 320px-wide wrapper is centered against the article's center line with calculated negative inline margins when the prose column is narrower than 320px. This keeps the unit unscaled and unclipped while allowing it to use the full viewport width at a 320px viewport. The component never stretches the generated iframe.

### Native Banner

The production branch preserves this exact order and identity:

- first, the external classic script with `async="async"`, `data-cfasync="false"`, and source `https://pl30995799.profitableratecpmnetwork.com/cd35885d41c8db0e720a6e017aadbf77/invoke.js`;
- second, the container with ID `container-cd35885d41c8db0e720a6e017aadbf77`.

The component appears once after the complete `Sources and verification` section and before previous/next navigation, related guides, or the footer. If a future guide layout does not render the source section, the Native Banner remains after the complete guide body and before article navigation.

The placeholder uses a restrained simulated height. The live minimum height is adjusted only after one controlled observation of the real production unit; no oversized blank area is guessed in advance.

## Page eligibility

The ad components are reachable only through the guide content collection and `src/pages/[category]/[slug].astro`. The collection schema limits categories to:

- `guides`
- `walkthrough`
- `islands`
- `bosses`
- `items`
- `achievements`
- `fixes`

This structural route and content-entry requirement permits concrete guide pages such as `/bosses/spider-crab/` and excludes category indexes, the homepage, search, About, Contact, Privacy, Terms, Disclaimer, 404, RSS, XML, JSON, sitemap, and other non-HTML outputs. Ads are not imported into `BaseLayout.astro`.

## Environment behavior

Centralize advertising decisions in one configuration module. Declare these public build variables:

- `PUBLIC_ADS_ENABLED`
- `PUBLIC_ADSTERRA_NATIVE_ENABLED`
- `PUBLIC_ADSTERRA_BANNER_320X50_ENABLED`
- `PUBLIC_ADS_DEPLOYMENT`

Real code loads only when all of the following are true:

- Astro is performing a production build;
- `PUBLIC_ADS_DEPLOYMENT` is exactly `production`;
- `PUBLIC_ADS_ENABLED` is exactly `true`; and
- the relevant unit switch is exactly `true`.

Behavior by context:

- Local development, CI, an ordinary local production build, and preview deployment: render both inert placeholders on eligible guide pages and include no Adsterra domains, key, container ID, or executable ad configuration.
- Production deployment with the total switch or an individual switch disabled: omit the disabled unit rather than showing a public placeholder.
- Production deployment with all switches enabled: render each approved unit exactly once on every eligible guide page.

The GitHub production workflow passes the production marker and three switches, validates their boolean values before building, and uses the existing Worker version upload and promotion order. No advertising key or private value is printed by validation or deployment logs.

## Client navigation and duplicate prevention

Because the site has no client router, every article navigation creates a new document. No lifecycle listeners, reinjection code, iframe cleanup, global `atOptions` manager, or client-side cache handling is added.

Duplicate prevention is structural:

- the 320x50 component is rendered at one build-time split point;
- the Native component is rendered once by `GuideLayout.astro`;
- neither component exists in the global layout or Markdown files;
- generated-site tests count scripts, the Native container ID, and component wrappers on representative and full guide sets.

## Privacy policy

Update `src/pages/privacy.astro` in the same production release. Its effective date is the actual deployment date.

The opening states that the site serves static informational pages and uses Adsterra for third-party advertising. The current production repository variable shows Google Analytics is enabled, so the existing conditional GA4 disclosure remains accurate and the policy must not claim that analytics is disabled.

Add an `Advertising` section that explains:

- Adsterra displays third-party advertisements;
- Adsterra and advertising partners may process IP address, browser and device information, requested page, approximate location, impressions, clicks, and anti-fraud or security signals;
- cookies, pixels, local storage, and similar technologies may be used to deliver, limit, measure, and protect ads;
- this site does not control every third-party advertisement;
- clicked advertisements lead to third parties with their own policies and terms;
- core guide content requires no account or purchase; and
- browser privacy controls, content blockers, or cookie settings may prevent ads without preventing access to the core guide text.

Keep the current Cloudflare hosting-log disclosure and link to the current official Adsterra policies:

- `https://adsterra.com/privacy-policy-managed/`
- `https://adsterra.com/cookies/`

Do not invent a company, address, DPO, consent record, or script-blocking behavior. Do not add a cosmetic cookie banner. The absence of a consent management platform remains an explicit legal/compliance item for human review even though the user authorized this production release.

## Internal metadata visibility

Keep `priority` and `verificationStatus` in frontmatter, the content schema, internal exports, build data, and any sorting or verification logic. Remove their internal display values from public UI:

- guide cards no longer show `P0`, `P1`, or `P2`;
- the guide hero no longer shows priority or the `mixed` status badge;
- the About page describes evidence handling without exposing the internal status vocabulary.

Do not change titles, descriptions, canonical URLs, structured data, the sitemap, publication dates, article ordering, or internal links. Ordinary uses of the English word "mixed" inside authored guide prose are not metadata labels and remain unchanged.

## CSP and Cloudflare behavior

Start with only the two known script origins in `script-src`:

- `https://pl30995799.profitableratecpmnetwork.com`
- `https://www.highrevenueformat.com`

Do not add a broad wildcard, remove the CSP, or pre-authorize speculative ad-network domains. After production deployment, open one guide page once, do not click the ads, and inspect the console and network activity. Add an origin to `frame-src`, `connect-src`, `img-src`, or `style-src` only when a concrete blocked request demonstrates the resource type and exact required origin.

If the real units require materially broad sources or a significant security-policy reduction, disable the advertising switches, rebuild and redeploy, and report the unresolved requirement instead of weakening the policy silently.

Check the live Cloudflare Rocket Loader setting. Regardless of its state, retain `data-cfasync="false"` on the Native script and confirm that the emitted HTML preserves the original script-before-container order.

## Test strategy

All code behavior follows test-driven development: add a focused failing test, confirm the expected failure, add the minimum implementation, then rerun the focused and full suites.

Source and unit tests cover:

- node-level Quick steps section recognition and complete-node serialization;
- missing heading, missing next H2, and malformed or unavailable rendered content;
- per-route warnings, zero-skipped summary, skipped-route summary, and the 80% broad-failure threshold;
- centralized environment behavior for placeholder, disabled-production, and live-production modes;
- exact script attributes, sources, key, dimensions, and order;
- the narrow CSP source additions without broad wildcards;
- public removal and internal preservation of priority and verification metadata.

Generated-site tests cover all guide pages and representative excluded pages in two builds:

1. Default placeholder build: eligible pages contain inert labeled placeholders; no generated file contains an Adsterra script domain, Native container ID, or live `atOptions` configuration.
2. Production-mode build: every eligible guide contains one Native script, one Native container ID, one 320x50 configuration, and one Banner script in the required order and body positions; excluded pages contain none.

The production-mode test inspects generated HTML only. It never opens the pages, executes the third-party code, requests an ad, refreshes an ad, or clicks an ad.

Use a real local browser against the placeholder build at CSS viewport widths 320, 360, 375, 390, and 414 pixels. For each width, verify that the 320x50 reserved body measures exactly 320x50, remains centered, and that `document.documentElement.scrollWidth` does not exceed `clientWidth`. Also inspect a desktop width for centering and normal-flow placement.

Run the repository's actual validation commands, including dependency audit, content validation, source tests, Astro and Worker type checks, production build, generated-site tests, duplicate metadata checks, internal-link checks, sitemap checks, and `git diff --check`.

## Release and rollback

1. Complete and review the code locally.
2. Generate an ordinary temporary Cloudflare preview in placeholder mode and verify that it contains no real Adsterra code.
3. Set the three approved production advertising switches and the production deployment marker in existing GitHub repository variables, then read back the variable names and update timestamps without printing ad keys.
4. Push the reviewed `main` commit and wait for the existing production workflow to pass.
5. Verify one live guide page, required excluded pages, response CSP, script counts and order, duplicate IDs, duplicate iframes, console errors, horizontal overflow, Native height, and Rocket Loader behavior without clicking or refreshing ads repeatedly.
6. Record the exact skipped-guide summary from the production build.

If production verification finds a content, layout, CSP, or third-party loading regression, turn off `PUBLIC_ADS_ENABLED`, run the existing production workflow, and verify that live pages no longer contain or request Adsterra code. Keep the approved unit configuration intact for diagnosis; do not delete or recreate Adsterra units.
